# 0029. Serverless on Lambda, with the database as the only always-on cost

**Status:** accepted

## Context
[ADR 0026](0026-aws-deployment.md) chose AWS and left the compute service open. Two facts decided it:

- **App Runner closed to new customers on April 30, 2026.** AWS points to ECS Express Mode instead, which puts
  Fargate tasks behind an Application Load Balancer.
- **Always-on compute is the bill.** At us-east-1 list prices, Express Mode is about $65–70/month (load
  balancer ~$17, two small Fargate tasks ~$27, public IPs ~$7, RDS ~$14). For a demo that sits idle most of
  the day, almost all of that is paying for nothing.

## Decision
Both services run as **Lambda functions from their normal container images**, through the
[AWS Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter), which turns Lambda invocations into
HTTP requests on the port the app already listens on. No application code knows it is on Lambda:

```dockerfile
COPY --from=public.ecr.aws/awsguru/aws-lambda-adapter:1.0.0 /lambda-adapter /opt/extensions/lambda-adapter
ENV AWS_LWA_PORT=8080 AWS_LWA_READINESS_CHECK_PATH=/actuator/health
```

```
CloudFront ─┬─ /            → S3 (console, private, origin access control)
            ├─ /api /demo /actuator → wms-core Lambda (in the VPC) → RDS MySQL 8.4 (no public address)
            └─ /agent       → ops-agent Lambda (outside the VPC) → Claude (ADR 0028), wms-core's public URL
```

| Choice | Why |
|---|---|
| One origin through CloudFront | The console, API and agent share a host, so there is no CORS to configure or get wrong |
| wms-core in the VPC, ops-agent outside it | wms-core needs only the database; the agent needs the internet and no database (ADR 0024). Neither needs a NAT gateway (~$32/month) |
| `Authorization` in the API cache key, max TTL 1s | CloudFront forwards that header only if it is part of the cache key; responses are `no-store`, so nothing is actually cached |
| RDS `db.t4g.micro`, one zone, 20 GB | The smallest real MySQL, same version as local and tests. ~$14/month, the whole bill |
| Credentials generated by Terraform | Database password, supervisor passcode and agent token never pass through a person; the state bucket is versioned, encrypted and private |
| Demo seeded by the supervisor's reset, not at startup | Seeding takes longer than a cold start may, and a public demo needs a reset anyway ([`DemoData`](../../wms-core/src/main/java/com/cloudwms/core/devdata/DemoData.java)) |
| Deploy on push, infrastructure by hand | [`deploy.yml`](../../.github/workflows/deploy.yml) runs all three test workflows and ships only if they pass, through an OIDC role that can push images and update the two functions and nothing else, trusted only for this repository's `demo` environment. `terraform apply` stays a deliberate step |

## Consequences
- About **$15/month**, nearly all RDS, currently paid by the account's AWS credits. Stopping the database
  between demos brings it to ~$2/month of storage. A budget emails at 50/80/100% and on a forecast, and at
  100% a budget action stops the database by itself, so the one always-on cost cannot run past the budget.
  Everything else is usage-priced and inside AWS's free allowances at demo traffic.
- **Cold starts.** The first request after an idle spell starts a JVM (a few seconds) before answering.
- The account's Lambda concurrency limit is 10, which rules out reserved concurrency, so the agent's daily
  budget is per instance. The Anthropic workspace's own spend limit is the hard cap.
- Moving to containers later is not a rewrite: the same images run anywhere, and the adapter does nothing
  outside Lambda.
